# 问题真实性与故事线核查：签发者—网关共谋

核查日期：2026-11-16。
代码证据：`paper_a/event_report/manuscript.tex`、`prototype/circuit.go`、`native.go`、`gateway.go`、`context_privacy_test.go`、`context_hiding_candidate_test.go`、`experiments/context_linkability.log`、`experiments/context_hiding_candidate.log`、`research/protocol_candidate.md`、`research/independent_security_audit.md`。

## 一、结论

**问题真实存在，不是编的。危害比我上一条回复说的更具体、更严重：共谋不是"可能关联身份"，而是确定性地还原出 ZK 证明专门对网关隐藏的精确时空坐标。**

**而且这个问题不是我提出的假想威胁——它违反了一条写在 IETF 标准里的规范性设计规则。** RFC 9576 §3.3 在定义"签发上下文"时明确规定：token challenge **必须对签发者保密**。本文主协议把由任务与挑战派生的 c 交给签发者，正是这条规则禁止的事。

同时必须更正我上一条回复的两处错误：

| 我上一条说的 | 核查结果 |
|---|---|
| "代价是新密码设计+改电路+重跑基准，数周量级且有做不出的风险" | **错。** 电路改动你们已经做完并跑通：`hiddenContextCandidate`，29,503 条约束（比主矩形电路 29,833 **更少**），Groth16 验证通过，上下文替换与持有人替换均被 R1CS 拒绝 |
| "检索范围内所有先例都没解决" | **错。** 这是匿名令牌/匿名凭证领域**被命名、被标准化、已有标准解法**的问题：Privacy Pass（RFC 9576/9578）的核心隐私目标就是它；CL 凭证的 commit-and-sign 是标准解法；车联网已有 Coconut 匿名凭证论文明确主张"抗 t−1 权威共谋"（DOI 10.1007/s12083-024-01645-7） |

**正确定位：问题真实、严重、且被标准承认；解法范式也已知。本文的增量不是"发现共谋"，而是——报告绑定这个具体需求，会朴素地重新违反这条标准规则；本文给出一个同时满足绑定与该规则的关系实例化，并形式化、实测。**

## 二、问题是否真实：代码级证据

### 2.1 主协议里签发者确实拿到 c

`manuscript.tex` L96–101：

> the participant computes a context-dependent holder value $h=H_{103}(s,c)$ and **presents it to the event issuer** as part of the receipt request. Following its event-observation procedure, the issuer signs $m=H_{104}(\mathbf{c},h,x,y,t)$ … **To apply its own issuance rules, the issuer must receive sufficient authenticated task and challenge information.**

要算出 $H_{104}(c,h,x,y,t)$，签发者**必须**持有 c。正文也明说它收到任务与挑战信息。**这不是实现疏漏，是关系设计本身要求的。**

而 $c=\mathrm{ContextField}(T,q,R)$ 正是由**任务 T、挑战 q、报告摘要**派生的（`native.go` L68–81）。**c 在结构上就是 RFC 9576 所说"必须对签发者保密的 token challenge"的派生物。**

### 2.2 精确坐标对网关隐藏，对签发者明文

`prototype/circuit.go` L28–42：

```go
type Circuit struct {
    Authority eddsa.PublicKey      `gnark:",public"`
    TaskID    frontend.Variable    `gnark:",public"`
    Context   frontend.Variable    `gnark:",public"`   // ← c 公开
    Nullifier frontend.Variable    `gnark:",public"`
    PolicyLo  [3]frontend.Variable `gnark:",public"`   // ← 只公开策略盒
    PolicyHi  [3]frontend.Variable `gnark:",public"`
    Secret            frontend.Variable              // 私有
    Credential        eddsa.Signature                // 私有
    Issuer            eddsa.PublicKey                // 私有
    IssuerCertificate eddsa.Signature                // 私有
    Receipt           eddsa.Signature                // 私有
    Event             [3]frontend.Variable           // ← (x,y,t) 私有见证
}
```

- **网关视图**：c、N、tid、策略盒 (ℓ,u)、权威公钥、证明、信封 R、挑战 q。**看不到 (x,y,t)**——这正是 ZK 区域/范围检查要保护的。
- **签发者视图**：c、h、**(x,y,t) 明文**（它按观察程序赋值并签名）、请求时刻、网络元数据。

### 2.3 连接是确定性等值连接，已实测

`prototype/context_privacy_test.go`：以 `c.String()` 为键建 `issuerRecords`，再用网关侧 `PublicStatement` 重构的 c 去查，命中即取出对应事件。

`experiments/context_linkability.log`：

```
RESULT synthetic_issuer_gateway_shared_context_join=2/2
SCOPE synthetic software demonstration of linkability when records are shared; no deployed issuer or network
```

**2/2 全中。这是 map 等值查找，不是概率猜测。**

### 2.4 危害的精确表述

> 签发者与网关合并记录后，以公共上下文 c 为键做等值连接，即可为**每一条被受理的报告**还原出签发者所签的精确坐标 (x,y,t)。

**后果：本文的核心隐私保证——"网关只知事件落在授权区域/时间窗内，不知精确位置与时间"——被完全绕过。而零知识证明本身仍然是完美零知识的。** 泄露不来自证明，来自协议让两个角色共享了一个确定性关联键。

**这个危害不依赖签发者能否识别车辆身份。** 即使签发者完全不知道车主是谁，网关仍然拿到了它本该拿不到的精确时空点。对车联网众包，精确位置+时间+报告内容的组合本身就是重识别素材。

**这就是"问题确实存在"的硬证据：它是当前关系设计的必然推论，已被你们自己的测试复现，且违反一条 IETF 标准明文规则。**

## 三、修复已经存在，而且更便宜

`prototype/context_hiding_candidate_test.go`：签发者只签 `(常量0, holder, event)`，**不接收 c、秘密、报告**（代码注释原文："The issuer signs this tuple only: it does not receive c, secret, or report."）。电路仍强制 `holder = H_103(Secret, Context)`，Context 仍是公开输入、由网关从收到的信封重构。

`experiments/context_hiding_candidate.log`：

```

SCOPE research candidate base circuit; issuer signature input is (constant,holder,event); role separation and privacy assumptions unproven; no network or extended circuit benchmark
```

| 项 | 主矩形电路 | 隐藏上下文候选 |
|---|---|---|
| 约束数 | 29,833 | **29,503（少 330）** |
| 诚实证明 | 通过 | 通过（Groth16 验证） |
| 替换上下文 | 拒绝 | **拒绝** |
| 替换持有人 | 拒绝 | **拒绝** |
| 签发者是否拿到 c | **是** | **否** |

### 3.1 为什么绑定没有变弱（关键论证，必须写进论文）

签发者**不需要知道 c**。它签的是参与者递交的 h。电路强制 h 必须等于用**网关重构的 c** 算出的值。所以"回执 ↔ 本次提交字节"的绑定是**由电路强制的，不是由签发者的知识强制的**。

攻击者要把旧回执配到新 c 上，必须拿到对新 h 的签发者签名 → 需要签发者再签一次 → 被签名不可伪造性挡住。实测 `substituted_context=R1CS_rejected` 正是这条路径。

**这是一个干净的角色分离：签发者只负责"我观察到了这个事件"，网关只负责"这次提交符合任务策略且字节匹配"，绑定由电路在两者之间强制。** 主协议把这两件事混在一起（要签发者"应用自身签发规则"、收任务与挑战信息），而**正是这个混淆制造了共享关联键**。

### 3.2 一个必须同时堵住的漏洞：挑战 q

`prototype/gateway.go` L76：`func (g *Gateway) Issue(now, ttl int64)` —— **不带任何身份参数**，只存 `pending[nonce] = Challenge`。所以 q 本身不是身份键，网关不知道谁取走了哪个挑战。这一点对修复有利。

**但主协议 L101 要求签发者收到任务与挑战信息。如果把 q 交给签发者，q 就成了新的共享键——修了 c 还漏 q。** 候选电路已做到只签 holder+event（不含 q），但正文 L101 那句必须相应改写为"任务资格与挑战有效性由网关强制，签发者只负责事件观察"，否则文字与修复不一致。

## 四、文献证据：这个威胁被承认吗（全部逐字核对）

**被承认，而且是 IETF 标准里的规范性隐私目标与部署假设，不是边缘顾虑。**

### 4.1 RFC 9576《The Privacy Pass Architecture》（2024-06，Informational）

来源：<https://www.rfc-editor.org/rfc/rfc9576.html>（本次实际抓取，全文已存本地）

**(a) §3.3 隐私目标第 4 条——这就是本文要的性质，原文：**

> **Redemption context unlinkability.** Given two redemption contexts, the Origin cannot determine which issuance and attestation contexts each redemption corresponds to, **even with the collaboration of the Issuer and Attester** (should these be different parties). This means that any information that may be learned about the Client during the issuance and attestation flows cannot be used by the Origin to compromise Client privacy.

**(b) §3.3"签发上下文"定义——规范性设计规则，原文：**

> Issuance context: … This **does not include the token challenge in its entirety, as that is kept secret from the Issuer during the issuance protocol.**

**这是本核查最重要的一条。标准明文要求 challenge 对签发者保密。本文主协议把 challenge 的派生物 c 交给签发者，直接违反它。候选构造恢复它。**

**(c) §3.3 威胁模型，原文：**

> **Colluding parties are assumed to have access to the same information** … However, Clients assume that **Issuers and Origins are malicious.**

**(d) §4 开头——共谋被显式建模，原文：**

> Entities drawn within the same bounding box are assumed to be operated by the same party and are therefore **able to collude. Collusion can enable linking of attestation, issuance, and redemption contexts.** Entities not drawn within the same bounding box (i.e., operated by separate parties) are assumed to not collude. **Mechanisms for enforcing non-collusion are out of scope for this architecture.**

§4.3 专设 **Joint Origin and Issuer** 部署模型（Origin 与 Issuer 同一运营方）——**这正是"网关与签发者共谋"的标准对应物**。

**(e) §3.1 步骤 5，原文：**

> This token can be validated by anyone with the per-Issuer key but **cannot be linked to the content of the token request or token response.**

**(f) §6.3 残留通道——标准自己承认时间关联，原文：**

> Side-channel attacks, such as those based on **timing correlation**, could be used to reduce anonymity set size. In particular, for interactive tokens that are bound to a Client-specific redemption context, **the anonymity set of Clients during the issuance protocol consists of those Clients that started issuance between the time of the Origin's challenge and the corresponding token redemption.** Depending on the number of Clients using a particular Issuer during that time window, the set can be small.

**(g) §6.2 残留通道——签发者公钥分区，原文：**

> Failure to apply a consistency check can allow **Client-specific keys** to violate Origin-Client unlinkability.

**(h) §6 开头——匿名集大小决定隐私价值，原文：**

> …one wherein there exists a redemption anonymity set of size two and another wherein there exists a redemption anonymity set of size 2^32 … **the smaller these sets become, the higher the probability of determining the "true" Client.**

**(i) §7.1——凭证共享是被命名的攻击，原文：**

> since tokens are not intrinsically bound to Clients, it is possible for malicious Clients to collude and share tokens in a so-called **"hoarding attack"**.

### 4.2 WICG Private State Token API Explainer（浏览器侧实现文档）

来源：<https://github.com/WICG/trust-token-api>（本次实际抓取）

> In Privacy Pass, tokens have an unlinkability property: **token issuance cannot be linked to token redemption.**
> The privacy of this API relies on that fact: **the issuer is unable to correlate its issuances on one site with redemptions on another site.** If the issuer gives out N tokens each to M users, and later receives up to N\*M requests for redemption on various sites, the issuer can't correlate those redemption requests to any user identity (**unless M = 1**).

并专设两节承认残留通道：**Key Consistency**（"If the server uses different values for their private keys for different clients, they can de-anonymize clients at redemption time and break the unlinkability property"）与 **Potential Attack: Side Channel Fingerprinting**（"If the issuer is able to use network-level fingerprinting or other side-channels to associate a browser at redemption time with the same browser at token issuance time, **privacy is lost**"）。

### 4.3 车联网场景的直接先例（有 DOI）

**Gong, Liang, Wang, Yao 等，《Anonymous credentials for the internet of vehicles》，Peer-to-Peer Networking and Applications，2024-01-31，DOI [10.1007/s12083-024-01645-7](https://doi.org/10.1007/s12083-024-01645-7)**（检索页：<https://www.x-mol.com/paper/1752749072989261824>）

摘要原文：

> To solve the problem of **malicious service providers excessively collecting and leaking user privacy**, we propose an anonymous credentials scheme based on **Coconut signature** for the IoV … our proposed scheme can effectively **resist collusion attacks from up to t-1 authorities** and **prevent malicious service providers from correlating vehicle user information, tracking user identities, and analyzing user behavior** … uses the techniques of **blind signatures, zero-knowledge proof, and secret sharing**.

**这是车联网里把"抗权威共谋 + 防服务商关联"写成明确主张的已发表论文。问题在本场景被承认，铁证。**

**Camenisch, Drijvers, Lehmann, Neven, Towa，《Zone Encryption with Anonymous Authentication for V2V Communication》，IEEE EuroS&P 2020，DOI [10.1109/EuroSP48549.2020.00033](https://doi.org/10.1109/EuroSP48549.2020.00033)**（OpenAlex 核实）

摘要原文：

> Vehicle-to-vehicle (V2V) communication systems are currently being prepared for real-world deployment, but they **face strong opposition over privacy concerns. Position beacon messages are the main culprit**, being broadcast in cleartext and pseudonymously signed up to 10 times per second … we introduce **zone-encryption schemes**, where vehicles generate and authentically distribute encryption keys associated to **static geographic zones** close to their location … **dynamic group signatures with attributes** … unlimited locally generated pseudonyms …

**顶会论文，直接处理"车辆位置隐私 + 地理区域 + 匿名认证"。这是本文位置隐私动机最有力的支撑，也是必须补引的相关工作。** 其"静态地理区域"与本文离散区域成员性思路同源，须正面比较而非回避。

### 4.5 结论

**把"签发者与验证方共谋破坏不可链接性"当作真实威胁，完全站得住：IETF 标准把它写成隐私目标与部署假设，浏览器实现文档把它写成 API 隐私前提，车联网已发表论文把它写成安全主张，密码学会议有以它命名的论文。这不是编出来的问题。**

**但同样必须承认：解法范式也已知。** 盲签发 / commit-and-sign（CL 凭证：用户对秘密做承诺，签发者签承诺，之后用 ZK 证明属性）就是标准做法；Privacy Pass 用 VOPRF/盲 RSA 实现同一目标。**候选电路的机制属于这个标准范式，不是新原语。**

## 五、承重墙：必须成立的假设与残留通道

**这一节决定故事会不会塌。好消息是：残留通道不是我编的，是 RFC 9576 §6 自己列出的同一批。**

### 5.1 签发者的观察能力（最关键）

签发者按"指定观察程序"给 (x,y,t) 赋值。**如果该观察程序本身能识别车辆长期身份（车牌识别、DSRC 证书、OBU 标识），那么身份↔事件已经在签发者手里，隐藏 c 挡不住身份↔报告的连接。**

必须显式假定：**签发者的观察程序产出事件坐标，但不产出参与者的长期身份标识。**

**注意：即使这条假设不成立，§2.4 的危害依然成立**——网关还原精确坐标与签发者是否知道身份无关。所以主张分两层：

- **层一（无条件成立）**：隐藏 c 消除确定性等值连接，网关无法从签发者日志还原精确坐标。**不需要签发者匿名观察假设。**
- **层二（需要假设）**：身份↔报告不可连接，需要签发者观察不产出长期身份。

**建议只主张层一，层二作为条件性讨论。** 这样故事不依赖难以辩护的假设。

### 5.2 残留的概率性关联通道（隐藏 c 挡不住）

1. **时空邻近**：签发者知道精确 (x,y,t) 与请求时刻；网关知道策略盒与受理时刻。任务盒窄、提交少时可做概率关联。**对应 RFC 9576 §6.3 的 timing correlation，且 RFC 已给出匿名集的精确定义（挑战时刻到赎回时刻之间开始签发的客户端集合）。本文可把它推广为"时空盒"版本。**
2. **网络元数据**：谁连到签发者。**对应 WICG 的 Side Channel Fingerprinting 节。**
3. **签发者公钥/配置分区**：`research/protocol_candidate.md` §5 已指出"A public RSU key may reveal its coverage area"。本文把 Issuer 设为私有见证缓解了这一点，但签发者集合本身仍可能泄露地理范围。**对应 RFC 9576 §6.2 与 WICG Key Consistency 节。**

**因此定理只能声称"消除共享的确定性关联键"，绝不能声称"共谋下不可链接"。** 这不是本文的额外弱点——**标准自己也是这么划界的**。把这一点写清楚，反而显得诚实且专业。

### 5.3 不能顺带声称的东西

- 不声称传感器数据真实（`independent_security_audit.md` §1：夹具本地生成全部签名，不是独立观察的 RSU 部署）。
- 不声称抗实时中继、抗凭证自愿共享（后者即 RFC 9576 §7.1 的 hoarding attack，是公开未解问题）。
- 不声称后量子（EdDSA/Groth16 不是后量子原语；ML-KEM 只覆盖传输层）。
- 不声称多网关/持久化 exactly-once（当前是单进程内存状态）。

## 六、故事怎么讲（推荐结构）

**不要把论文改写成"抗共谋论文"。保留原问题主线，把共谋缺陷作为"为什么关系必须这样设计"的论证。**

### 6.1 真正的非显而易见性在哪里（这是关键）

Privacy Pass 之所以容易做到签发—赎回不可链接，**部分原因是它的令牌根本不绑定任何丰富内容**——它只是证明"这个客户端通过了某种粗粒度认证"的无记名令牌。

**本文的需求相反：令牌必须同时绑定 (i) 特定凭证、(ii) 签发者实际观察到的特定事件、(iii) 本次提交的确切字节。** 而"绑定到确切字节"最自然的实现就是把字节摘要（即 c）交给签发者一起签——**这一步立刻重新引入标准禁止的共享键。**

> **所以真正的设计问题是：如何在对签发者隐藏绑定键的同时，仍然让证明强制"回执 ↔ 本次字节 ↔ 观察事件"三者同一。**

**这就是不能"直接用 Privacy Pass"的原因，也是本文关系的非显而易见性所在。** 它不是新原语，是一个**在内容绑定与签发者输入保密之间存在真实张力的具体关系设计**，而且本文的解法比朴素解法约束更少。

### 6.2 推荐叙事

1. **问题**：报告受理必须把凭证、签发者事件、所提交字节绑成同一陈述，否则可被交叉替换。（真实，已有消融证据）
2. **朴素做法及其缺陷**：最自然的绑定是让签发者把上下文 c 一起签进去。**这违反 RFC 9576 §3.3"challenge 对签发者保密"的规则；我们实测其后果：网关与签发者合并记录后，以 c 为键 2/2 还原出 ZK 专门隐藏的精确时空坐标。** 零知识性质没被破坏，破坏它的是协议共享了确定性关联键。
3. **本文的构造**：签发者只签 h=H(s,c) 与事件，不接收 c；绑定改由电路强制。**绑定保持，共享键消失，约束反而更少（29,503 < 29,833）。**
4. **形式化与实测**：定义"共谋下精确位置不可还原"，给 PRF 假设下的归约；消融证明三项绑定各自必要；连接实验证明朴素做法失效、本文构造消除该键；四电路基准。
5. **边界**：概率性时空关联、签发者观察能力、网络元数据是显式假设与局限——**与 RFC 9576 §6 自己列出的通道一致**。**不声称共谋下完全不可链接。**

### 6.3 这个故事的优点

- **它回答了现稿从未回答的问题：为什么关系长这样。** 现稿只是断言设计，读者看不出非显而易见性。
- **它有外部权威锚点**：违反的是 IETF 标准明文规则，不是作者自设的稻草人。审稿人无法说"这个问题是你编的"。
- **它有真实设计张力**（内容绑定 vs 签发者输入保密），而不是"把已知技术装进系统"。
- **它有实测反例**（2/2）和**代价更低的修复**（少 330 条约束），两样都是硬证据。
- **它不需要声称新原语**，因此不会被"这些都是已知技术"一击致命。
- **它的局限与标准自己的局限一致**，显得诚实而非心虚。

### 6.4 贡献列表相应改为

- a) 报告绑定的零知识受理关系，及**内容绑定与签发者输入保密之间张力**的形式化刻画；
- b) **消除共享上下文关联键的构造**：签发者不接收上下文，绑定由电路强制；给出共谋下精确位置不可还原的定义与归约，实测朴素构造的确定性连接（2/2）与本文构造的拒绝行为；
- c) 三项绑定必要性的消融量化 + 四电路可执行原型与代价（含隐藏上下文构造约束数更低这一结果）。

## 七、要做的工作（与不做的承诺）

### 必须做

1. **形式化定义与归约**：定义游戏——敌手拿到签发者日志与网关日志，猜测某条被受理报告的精确单元；在 H_103 为密钥化 PRF、s 高熵假设下，优势不超过在策略盒内随机猜。给出归约。**这是候选代码注释里"privacy assumptions unproven"所指的空缺。** 可直接借用 RFC 9576 §6.3 的匿名集表述并推广到时空盒。
2. **把候选扩到区域/可追责/活跃集三个电路**，重跑约束数与基准（当前候选只有基础矩形电路，日志明写 `no extended circuit benchmark`）。
3. **正文一致性改写**：
   - L101"签发者须收到任务与挑战信息"→ 改为角色分离表述（否则文字与修复矛盾，且 q 会变成新的共享键）；
   - L77 与 4.7 角色专属隐私段（docx 块 74）→ 从"承认关联"改为"给出消除该键的构造 + 残留通道"；
   - 系统模型 → 加签发者观察能力假设（§5.1）。
4. **补引（全部已核实）**：RFC 9576 / 9578；Gong 等 IoV Coconut 匿名凭证（10.1007/s12083-024-01645-7）；**Camenisch 等 Zone Encryption（10.1109/EuroSP48549.2020.00033）**；Bringer–Chabanne–Patey NSS 2013；CL 2001。**不补引而声称抗共谋新颖，会被直接否掉。**

### 需要作者批准才能做（违反当前"不新增实验"硬约束）

5. **残留通道的量化实验**：在合成轨迹上测"时间+空间邻近关联"成功率随任务盒宽度与提交密度的变化，给出匿名集大小。**这是新增实验**，能把 §5.2 从"免责声明"变成"量化边界"，显著增强说服力，但需作者明确同意并新跑数据。

### 明确不做

- 不声称新密码原语；不声称首次发现签发者—验证方共谋问题；
- 不声称共谋下完全不可链接；
- 不声称传感器真实性、抗中继、后量子、多网关持久化。

## 八、与既有调研文档的关系

- `research/protocol_candidate.md` §3.3 曾提出用**新鲜随机盐 eta** 做持有人承诺 `C_holder=H(s,eta)`。那是另一条路：让签发者无法跨事件链接 h，但**该文档 §3.4 仍让签发者签 context_digest**，共享键 c 仍在。**本文候选走更直接的路：把 c 从签名消息里去掉。** 两者可叠加（eta 防签发者侧跨事件链接，去 c 防签发者—网关连接），但叠加需重新论证绑定与约束代价，**不应未经实现就写进贡献**。
- `research/independent_security_audit.md` §5 曾指出 ContextField 含**无盐 SHA-256 报告摘要**可被离线猜测。当前实现已改为对 ML-KEM 信封（随机化）取摘要，该具体问题已缓解；但它提醒我们：**c 的公开性本身就是需要论证的设计选择**，共谋连接是同一根源的另一个后果。
- `初版问题_新方案头脑风暴.md` 已确立"不能宣称已经发现隐私漏洞""不能把已知原语当新贡献"的纪律。本核查遵循同一纪律：**§2 的连接是当前关系设计的必然推论且已实测，不是对某个已发表系统的漏洞指控。**
