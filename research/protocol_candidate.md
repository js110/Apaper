# Candidate relation: task-scoped anonymous event-bound reporting

Status: design specification, not a completed implementation, formal reduction, empirical finding, or claim of priority. Prepared 2026-11-04 for the initial PCVCS task. Authority for pre-existing design: the user-supplied TST-Audit article, pp. 1 and 4–9, and the initial PCVCS PDF, pp. 1, 6–7, 10–12. This specification is deliberately narrower than full vehicle deployment and retains the initial research objective: a single task-compliant report, identity/location/time privacy, and at-most-once-per-task reporting. Treat all proposed primitives as established components.

## 1. Positioning against the actual prior work

Initial PCVCS proposes RSU-issued presence tokens, task region and time proofs, task-scoped linkability, and ML-KEM-protected transport. Its described broadcast token contains an RSU identifier, a window, a nonce and an RSU signature. As a conditional counterexample to the broadcast formulation, a party receiving the same signed token learns the same transferable message; merely committing to it does not by itself prove that a particular credential holder was the physical receiver. This is an analysis of a specified public-broadcast abstraction and is not proof of a vulnerability in every PCVCS implementation: acquisition restrictions and further checks must be separately inspected.

The published TST-Audit paper defines, at interface level, anonymous credentials, proof of hidden `(l,t)` within publicly reported `(grid,epoch)`, nullifiers scoped to grid/epoch and binding to the assigned edge, with a possible edge-issued challenge. Its macro task is coverage auditing and the paper explicitly excludes sensed-content truthfulness. Its abstract micro-proof interface does not specify payload contents, a concrete task policy digest, or a report-payload commitment jointly verified with a concrete witness receipt; this means only that the published interface leaves those details open, not that it excludes any implementation, that a vulnerability exists, or that the proposed feature is new relative to all literature. Its per-grid/epoch uniqueness is a different business rule from at-most-one contribution per task.

Potential contribution requires demonstrating a concrete, meaningful difference from both works, particularly same-holder/same-report/same-task/same-witness consistency, and an actual executable cryptographic realization and evaluation. A suitable honest statement is **“a report-specific realization and evaluation of a jointly bound authentication relation”**, conditional on a full literature and implementation audit. It is not “first anonymous time-location proof”, “first privacy-preserving sensing” or “first nullifier”.

## 2. System, policy and encoded context

Entities: enrollment authority `A`; task issuer/gateway `G`; authorized observation issuer `W`; participant `V`; optional report recipient. For an initial prototype the gateway and recipient can be the same trusted configuration holder; `A` and `W` use independently generated signature keys. The signature verification keys are hard-wired circuit constants or reconstructed from an authenticated task configuration, not accepted from the prover unchecked. A single issuer is adequate for the first runnable model. Multiple issuers, issuer-set membership and revocation are separate features.

An immutable task record is `(version, task_id, policy_version, grid_root, t_min, t_max, issuer_pk, authority_pk, domain)`. `grid_root` commits to a tree of permitted discrete cells, permitting irregular authorized regions rather than silently restricting the original requirement to rectangular geometry. A participant proves membership of its privately signed cell `g` in this tree. For a guarantee about a continuous polygon rather than just cell membership, the policy compiler must include a cell only if that whole cell lies in the polygon; boundary-intersecting cells require an exact checked predicate or conservative rejection. State the projection, grid resolution, boundary inclusion and coordinate rounding; otherwise the Merkle proof says nothing about physical polygon containment. Time window is inclusive `[t_min,t_max]`, stated explicitly, in one integer unit. Correctness of the real-world mapping from location to cell is an **issuer/measurement assumption**: the circuit can verify only the signed cell and its membership, not that the physical car occupied that cell. If no Merkle policy is implemented, claim only the narrower actually implemented predicate and do not describe arbitrary authorized regions as supported.

Gateway creates one unpredictable challenge `nonce`, a task-specific trusted absolute expiry `expiry`, and server-side state `(task_id, nonce, expiry, status)`. Context is a collision-resistant, domain-separated, canonical encoding of all fields. The public policy root, bounds, authority and issuer keys and clock are derived from trusted gateway configuration; a malicious prover cannot choose an easier policy, substitute a key, or extend expiry.

Canonical encoding is part of the security relation. Fix byte order, lengths, domain tags, maximum sizes and integer bounds; reject non-canonical input rather than ambiguously reducing arbitrary byte strings to a field. Hash concatenation is length-separated. `task_id` must uniquely identify a specific business quota and authorization context; changing a challenge must not change its deduplication domain. If a task legitimately permits multiple reports, the desired quota must be stated instead of representing the one-per-task rule as universal.

## 3. Concrete relation and workflow

Let `H_C` be the field-friendly hash instantiated and tested in gnark; use separate domain tags for each role, fixed field encoding and the actual standardized implementation parameters. Let `H_bytes` be SHA-256 over a canonical length-prefixed encoding of the report bytes and an independently sampled 256-bit salt `rho_R`. Let `PRF_s` be an explicitly defined and circuit-implemented pseudorandom function. A keyed construction over MiMC must be accompanied by its precise keyed security assumption; a public collision-resistant hash is not automatically a proven PRF. HMAC-SHA-256 is a candidate if actually implemented in-circuit; benchmark its cost, do not assume it is cheap.

1. **Enrollment**: a participant chooses high-entropy secret `s`; authority signs a credential message `m_A = H_C(tag_cred, H_C(tag_id,s), credential_expiry, attributes)` using its authorized key. Authority verifies and enforces the identity/device enrollment rule outside the ZK circuit. The signed credential and secret remain private witnesses. The minimal prototype can use an authority signature on an opaque commitment; a blind-issuance claim requires a separate implemented protocol. Revocation is out of scope unless a current issuer-signed root/expiration check is actually implemented.
2. **Report commitment**: for bytes `R`, sample independent `rho_R` and compute `h_R = H_bytes(encode(R),rho_R)`. The gateway/authorized recipient obtains `R,rho_R` via an authenticated confidential channel and reconstructs `h_R` itself; the circuit should not accept a prover-provided digest as evidence of the delivered payload unless this outer check is performed. This is exact bytes binding, not proof of measurement truth. `rho_R` must not appear in a public transcript if it is relied on against offline guessing. If the transport is not implemented, explicitly say the plaintext evaluation is only an application-integrity prototype and make no confidentiality claim for the payload.
3. **Fresh holder commitment**: sample private high-entropy `eta`; compute `C_holder=H_C(tag_holder,s,eta)` and disclose `C_holder` to the witnessing issuer. It is randomized per event; it need not be public to the gateway if hidden as part of the witness. Its binding/hiding properties must be based on a justified hash model and sufficient randomness, not presented as unconditional.
4. **Issue receipt**: after its own legitimate presence/time check, `W` signs `m_W=H_C(tag_receipt, context_digest, h_R, C_holder, g, t)`; the complete `context_digest` contains the trusted task/policy version, challenge, expiry, and domain. `W` must check the challenge and task eligibility in the assumed attestation mechanism. `g,t` are only issuer-asserted quantities: assuming an honest `W`, its stated observational procedure must connect them to the intended physical event. A signature on a vehicle-supplied location is not an independent location proof.
5. **Proof relation**: public instance is `(context_digest, h_R, N, grid_root, t_min, t_max, pk_A, pk_W)` with constants trusted/reconstructed by the gateway; private witness is `(s, credential_expiry, attributes, sig_A, eta, g, t, merkle_path, sig_W)`. Constrain:
   - credential signature by `A` on the correctly encoded credential message, eligibility and expiry as implemented; expiry must be compared against a trusted gateway-provided current time or another explicitly specified trusted freshness value, not a prover-chosen time;
   - `C_holder=H_C(tag_holder,s,eta)`;
   - `Verify_W(sig_W, H_C(tag_receipt,context_digest,h_R,C_holder,g,t))=1`;
   - `MerkleVerify(grid_root, g, merkle_path)=1` with valid path direction bits;
   - range-check `g`, `t`, `t_min`, `t_max`, expiry and indices on fixed-width integers; compare `t_min ≤ t ≤ t_max` with constrained bits;
   - `N=PRF_s(tag_nullifier,task_id)`, where the task ID in the computation is identical to that encoded in context and public configuration. If `context_digest` is public while its fields are not available in-circuit, expose them or recompute the digest in-circuit so that task-id equality is actually constrained.
6. **Atomic acceptance**: `G` decrypts if implemented and computes `h_R`; verifies the configured public statement and valid proof; checks challenge matches live task and trusted clock; atomically commits `(task_id,N)` and consumption of nonce with accepted report in one durable transaction. Failed verification must not consume a live challenge. Concurrent gateways require shared transactional storage; an in-memory single process supports only that stated scope. A retry may return the previous idempotent result, but must not create a second accepted contribution.

Important implementation detail: the holder commitment is signed by the issuer and recomputed from the same credential secret inside the proof. Signing `h_R` but failing to constrain that same digest against the byte sequence received by `G`, or deriving a nullifier from a secret unrelated to the credential, defeats the intended binding. Writing field names in a paper is insufficient; adversarial witness tests must try changing each equality independently.

## 4. What can and cannot be established

**Algebraic correctness (candidate).** Given a valid credential, a valid issuer signature over the same correctly encoded task/context/report/holder/cell/time, an authorized Merkle path, in-window time, and a fresh unused challenge and nullifier, a correctly constructed proof should verify and gateway should accept once. This is a testable implementation property; completeness and all required circuit constraints need proof.

**Conditional evidence binding (candidate).** Under knowledge soundness of the chosen circuit-specific SNARK and setup, signature existential unforgeability, collision resistance of the context, report and holder bindings, and the checked external report digest, an accepting proof yields a witness that passes those exact checks. An adversary changing the delivered report, task, nonce, authorized cell, timestamp, issuer key or holder secret while reusing a fixed issuer receipt must either obtain another signature, find a binding collision, break soundness, or exploit a missing/incorrectly encoded constraint. This is a reduction outline, not a completed proof. Credentials may be issued to adversary; bound target must be defined as a signed event, not as “the data are true”.

**Task-scoped duplicate prevention (candidate).** If unique enrollment per participant/device is enforced, `s` is not shared, a correct PRF is used, and `(task_id,N)` update is atomic, two distinct accepted reports with the same `s` and task ID produce identical `N` and at most one contribution is recorded. The argument does not prevent a single physical person or device obtaining multiple credentials, deliberate credential sharing, registration compromise or relay of an authorized device. Do not confuse a repeated request's idempotent acknowledgement with a new accepted contribution.

**Privacy (conditional and role-specific).** The verifier sees policy, task, nonce, expiry, nullifier, report digest, proof and signer/authority keys; the recipient sees report bytes and salt. The receipt issuer sees the event commitment and its own observed context. ZK can hide the credential, cell, time and receipt from the verifier only if those are private in the actual relation and no public issuer key, task, report, network metadata or collateral field reveals them. A public RSU key may reveal its coverage area. Nullifier linkability within one task is intentional. A claim of cross-task unlinkability requires an explicit PRF/hiding assumption and side-channel scope and cannot be established by a few distinct sample hashes.

**Physical limits.** A signed cell and timestamp become evidence of location/time only under an explicitly trusted issuer's physical observation, secure clock and accurate mapping; a report digest does not prove that `R` was generated by a sensor at the signed instant. A credential-bound holder commitment limits evidence copying by a party who lacks the secret, but does not rule out a credential owner voluntarily sharing secrets, device borrowing, collusion or a real-time relay. A TEE attestation alone is not proof of truthful sensor input. Those attacks are scope boundaries unless a real distance-bounding protocol or trusted data-acquisition path is implemented and evaluated.

**Security parameters.** For the available Groth16/BN254 stack and twisted Edwards EdDSA, document curve, hash, setup assumptions, field/bounds and output sizes; do not label the complete construction post-quantum or IEEE 1609.2 credential compatible. Keep the report's transport encryption as an explicitly separate option from the zero-knowledge relation; if ML-KEM is not actually implemented, omit any post-quantum transport claim.

## 5. Implementation-oriented checks

The minimal monolithic circuit does not require recursive proof folding. Use two in-circuit issuer/credential signature verifications, a fixed-height Merkle region membership, fixed-width constrained time comparisons, holder commitment equality and a genuine in-circuit nullifier PRF. Authority and RSU keys can initially be trusted *public* parameters; this admits coarse location inference from a known RSU, so avoid claiming issuer anonymity. An issuer-set Merkle membership with private key can be a later optimization/extension, not an unimplemented initial claim. Ensure the signature and MiMC implementations use the same curve, message bytes/field encoding, hash parameters and key representation as witness generation. For all signed fields evaluate public inputs supplied by the gateway, not unconstrained hints. Compare the generated R1CS against the actual circuit, and distinguish proof size from total request size, public witness, credential issuance, signature creation, setup and transmitted payload.

Hash commitments use fresh salts, but for scientific honesty evaluate whether opening salts to different actors and sender network metadata enable association. Time comparisons must use range-constrained unsigned integers; field inequalities without bit decomposition can accept wraparound. Merkle path positions, boolean flags, same task/root, exact signature scalar/public-key serialization, domain separation, and sender-held secret must be covered by tests.

## 6. Falsifiable verification plan

Test every failure at the layer where it should be rejected. Circuit negative tests cannot simply change a private witness while retaining a signature if the only intended check is an external gateway check; include both prover-generated adversarial witnesses and malformed public statements. Use real verification and report test counts without treating deterministic examples as exhaustive security proofs.

| Scenario | Test construction | Expected result under stated assumptions |
|---|---|---|
| Honest completion | valid credentials, receipt, allowed cell, in-window time, new N and nonce | accept once |
| Payload replacement | keep receipt/proof, alter submitted `R` and let gateway recompute digest | reject |
| Receipt substitution | copy signature across reports/challenge/task while keeping fresh claimed fields | reject |
| Holder substitution | attacker uses copied receipt/commitment with its own credential secret | reject, assuming no secret sharing |
| CA/issuer spoofing | self-selected keys or signature under other key | reject; gateway must not trust supplied keys |
| Region and time violations | unregistered cell; lower/upper time just outside window; malformed Merkle direction | reject; exact inclusive endpoints accept |
| Range and encoding | overflow/field wrap, noncanonical byte encodings, reordered policy encoding, wrong domain tag | reject by parser or circuit |
| Unauthorized policy | replace public root/window/expiry with one chosen by prover | reject using gateway-owned configuration |
| Challenge replay | same nonce after acceptance, expired nonce, unknown nonce | reject |
| Same task, fresh nonce | independently valid second proof with same credential and task | same N, one accepted contribution |
| Different task | same secret with different task IDs | distinct marker in test; this check alone proves no unlinkability theorem |
| Concurrency and crash | parallel same N/different nonces; failure between check/update | one durable contribution, no partial state |
| Relay/credential sharing | authorized holder cooperates remotely or shares `s` | *not claimed prevented*; record as explicit expected limitation |
| Sensor fraud | arbitrary stale/fabricated R signed by a compliant but input-oblivious issuer | *not claimed prevented*; demonstrates need for trusted acquisition |

Meaningful baselines: (A) an explicitly reconstructed abstraction of the initial broadcast-token specification, with acquisition assumptions and differences clearly stated; (B) issuer-signed report/context but no holder equality; (C) holder equality without nullifier; (D) full relation. A malicious-policy test should not compare systems operating under different trust assumptions. For originality compare the exact published TST-Audit interface, task versus grid/epoch nullifier scope, public grid, and whether payload/issuer receipt relation is specified, rather than treating its published macro coverage goal as defeated by a report-level method. Do not present a deliberately weakened reference as a published full implementation. Reproducible cost tests: compiler/curve/backend/version, constraint counts by component, setup time and memory, proof generation and verify distributions, proof vs public witness vs complete message bytes, policy-tree height, actual single or multi issuer count, credentials and report sizes, same hardware; publish raw trials and scripts.

## 7. Optional multi-issuer extension, not the core paper by default

Suppose N pre-enrolled independently identified trust domains include at most f Byzantine issuers and at most r additional honest issuers whose signed uncertainty sets omit the reference event. The prover collects q signatures on the same holder/report/task/challenge; every signed set `U_i` must be wholly contained in public policy `P`. For `q > f+r`, at least one selected signer is honest and covers the true event, so `z*∈U_i⊆P`. A formal proof requires uniqueness by trusted domain, all signatures tied to the **same event**, and valid physical coverage premise. Near a boundary a true positive can be rejected if too few intervals are wholly inside P. This is more conservative than the prior full depth-set rule and is not mathematically equivalent. It can permit missing signers when q valid signatures arrive, but more signatures and a new roster/selection model are required; no claimed speedup without measurement. Multi-source ZK/threshold components have precedents, including [ERC-8262 review proposal](https://eips.ethereum.org/EIPS/eip-8262), [PG](https://ir.cwi.nl/pub/34722) and [CRSF preprint](https://arxiv.org/abs/2609.01096). Selection alone cannot eliminate correlated issuer error, device fraud, collusion or relays.

## 8. Ready-to-write versus not yet established

- Ready for a paper draft as conditional method: threat model, encodings, precise accepted relation, data-flow and proof obligations, followed by tests actually performed.
- Not yet established: implemented anonymous credential, all signature and Merkle circuit constraints, report encryption, non-simulated time/location anchoring, replay persistence, empirical costs and any strict novelty claim.
- Reuse code only after auditing exactly what the old reference adapters and current GNARK code execute. Existing experiment results from either paper do not measure this new proof relation and must not be repurposed as new results.
- Before submission, compare exact techniques and reproducible implementations against your own TST-Audit and close literature, and have authors validate the formal definitions and all scientific claims. No paper should assert conclusions that have not been tested or proven.
