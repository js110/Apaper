# Event-report circuit security review

Reviewed 2026-11-04: `paper_a/event_report/prototype/circuit.go` and the concurrently appearing `native.go`. This is an early source review, not a formal audit or successful proof execution. Changes made after this review require rechecking. `go list` could not download gnark from `proxy.golang.org` (connection timed out); algebraic counterexamples below are predictions to test, not observed results. The primary library source consulted is [gnark v0.14.0 EdDSA verifier](https://raw.githubusercontent.com/Consensys/gnark/v0.14.0/std/signature/eddsa/eddsa.go) and [bounded comparator](https://raw.githubusercontent.com/Consensys/gnark/v0.14.0/std/math/cmp/bounded.go).

## 1. What the current circuit actually constrains

The public fields are authority point, task ID, opaque context field, nullifier and 3D axis-aligned policy bounds; the secret witness comprises a participant secret, authority credential signature, private issuer public point, authority signature on that issuer point, issuer receipt signature, and a private three-dimensional integer event. The circuit enforces:

- `secret != 0`, and an authority signature on `MiMC(101, secret)`;
- an authority signature on `MiMC(102, issuer.X, issuer.Y)`, keeping the certified issuer key private;
- public `N = MiMC(105, secret, taskID)`;
- receipt verification for `MiMC(104, context, MiMC(103,secret,context), eventX,eventY,eventT)` under the certified issuer key;
- bit-decomposed 32-bit event and policy coordinates and inclusive interval comparisons.

This is a **certificate-authenticated private issuer key**, not a Merkle issuer-root construction. No Merkle membership in issuer or region trees is present. There is one issuer, one certified event point, and a 3D box. No credential validity date, credential revocation, multiple issuer diversity, proof of actual physical location, encrypted payload, or autonomous anti-replay state is enforced by the circuit.

## 2. High-priority issue: neutral-element issuer key under certified-key enrollment

The gnark v0.14.0 verifier checks its EdDSA equation after multiplying by the cofactor. It explicitly invokes `AssertIsOnCurve` for an intermediate point `Q`, but the linked implementation does not explicitly validate the input public key or reject the identity point. The circuit's private issuer point is certified by the authority, but neither the circuit nor a demonstrated registration service yet validates issuer key quality. If an attacker can obtain an authority signature certifying the twisted-Edwards neutral key `A=(0,1)`, then the candidate signature `R=(0,1), S=0` satisfies the cofactored group equation for **any** receipt message. This is a concrete algebraic failure mode contingent on authority issuance of that malformed key; it is not evidence that such a certificate exists in the current test fixture or that a registered, validated nonidentity issuer can be forged.

**Required negative control:** have the real fixture authority sign `MiMC(102,0,1)` as an issuer certificate; set `Issuer.A=(0,1)` and set the receipt signature `R=(0,1),S=0`; keep a legitimate user credential and in-window event but do not use any issuer secret. Before claiming arbitrary issuer unforgeability, run a real circuit-solver and proof test and ensure enrollment/circuit rejects the key. If it succeeds, a legitimate trusted CA certificate for this point makes all receipt messages trivially forgeable. Independently test off-curve points, low-order keys and any mixed-torsion/non-prime-subgroup cases supported by the curve.

**Mitigation boundary:** strictly validate issuer registration, including canonical point parsing, on-curve, rejecting identity and the applicable prime-order subgroup requirement, before authority issues an issuer certificate. Because the issuer point is a private circuit witness, an in-circuit check is stronger against an overly permissive signing service; alternatively explicitly model and test a trusted authority that certifies only sound keys. For the *public* authority key, the gateway must pin and validate its configured key; allowing an attacker to select authority is a trivial total authorization failure. Do not assume a helper that parses bytes externally constrains arbitrary private witness points inside the R1CS. Likewise test the receipt `R` point and signature scalar canonicality, or clearly state and justify the security of the library verifier and authorized-key validation being used.

## 3. High-priority issue: task, context, policy and report consistency is external

`TaskID`, `Context`, `PolicyLo`, and `PolicyHi` are independent public circuit fields. The receipt signs `Context` and the nullifier uses `TaskID`, but the circuit never computes an equality tying `TaskID` or the policy bounds to `Context`. This is **not automatically an exploitable bug** when `PublicStatement` is called by a trusted gateway using the same immutable `Task`, actual payload, and its own stored challenge, and only the resulting public witness is used in `Verify`. It is a failure if a gateway accepts these fields from the prover as authoritative.

For example, with a legitimate receipt and unchanged context, an owner who knows the credential secret can recompute `N` under another public `TaskID` and regenerate a valid proof; without trusted reconstruction, this changes the uniqueness scope while preserving the receipt. Likewise, changing the public policy bounds can make an event pass a wider box without changing the issuer-signed context. The code is therefore a cryptographic relation plus a **mandatory verifier-side statement reconstruction invariant**, not a self-contained proof that its task/context/policy values are consistent. Either constrain the encoding relation in-circuit or specify and test this external trusted boundary.

`native.go:ContextField` hashes the actual report bytes and a JSON-encoded struct containing the task, challenge and expiry; `TaskField` hashes the task ID. `PublicStatement` recomputes both plus policy bounds, which is a reasonable building block, but is not itself a full gateway. Verify that no acceptance path uses a public witness generated by the prover, and ensure the authority bytes and `Task` are trusted configuration, the challenge is read from server state, and actual received bytes are passed to `ContextField`. The code does not yet demonstrate stable configuration across duplicated task IDs, challenge storage, trusted time or transactional deduplication. Credentials are task-independent and have no validity/revocation attribute in this circuit.

**Required negative controls:** change exactly one of trusted-task ID, each policy endpoint, report bytes, nonce, expiry or authority; reconstruct verifier input using `PublicStatement` and expect a formerly valid proof to fail. Separately test that the relation alone accepts a changed `TaskID` and recomputed `N` with unchanged context and signed receipt, and a widened policy with unchanged context, because these demonstrate why gateway reconstruction is part of the theorem. Such a test documents a security boundary rather than a published exploit if the implemented verifier never accepts inconsistent fields.

## 4. Report content confidentiality and dictionary leakage

`native.go:55–61` computes `SHA256(report)` with **no random salt**, encodes it with known task/challenge in a deterministic JSON struct, hashes and reduces to a public field `Context`. If an external observer learns the public statement and task/challenge and the report comes from a small or guessable domain, they can compute `ContextField` for candidate reports and compare the results. Hashing the report again in the JSON transcript or adding a public nonce does not prevent this dictionary attack. Report secrecy is not supplied by the circuit, and actual payload transport confidentiality has not yet been implemented or assessed.

If payload privacy against observers is a target, generate a secret 256-bit independent salt per report, include `SHA256(length || report || salt)` in context, and deliver `report,salt` only over an authenticated confidential channel to the authorized gateway. That gateway must recompute it from the actual received payload; the issuer signs the salt-derived context. This still does not conceal the report from the authorized recipient or from data disclosed elsewhere and is only as secret as the salt/channel. A salted commitment may not be appropriate if the threat model intentionally permits the complete report to be public; document the policy either way.

**Executable demonstration:** build the same task/challenge and public context from the true report in a small known set, enumerate candidate bytes with `ContextField`, and identify which candidate matches. With a hidden high-entropy salt unavailable to the external observer, repeat the relevant interface-level reasoning; do not misrepresent a mere failed finite dictionary search as a formal privacy proof.

## 5. Credential and nullifier claims need precise assumptions

- The circuit correctly uses the same `Secret` for the credential message, holder binding and nullifier, but a nonzero constraint does not enforce 128/256-bit entropy, one registration per person/device, non-transferability or custody. The prototype fixture samples a field element; this is a fixture behavior, not a verified issuance protocol.
- The registration authority authorizes a deterministic `MiMC(101,s)` commitment. Specify who chooses `s` and what the authority sees or retains. The `Fixture` owns all private data in one process; no blind issuance or anonymity against the authority is implemented. Anyone knowing `s` can calculate task markers. Membership/issuer privacy from the gateway is conditional on ZK and on the absence of public identifiers, network or payload metadata that reveal it.
- `MiMC(105,s,TaskID)` is called a nullifier hash; collision resistance alone does **not** establish a standard PRF or cross-task unlinkability. Either justify the exact domain-separated keyed-hash/pseudorandomness assumption under the field hash construction, or implement and benchmark a documented PRF. A few different task outputs do not prove unlinkability. In the same task the stable tag intentionally links duplicate submissions.
- The holder is `MiMC(103,s,Context)`, i.e. deterministic for a fixed context, not independently random. It varies with a correctly fresh unpredictable challenge. State exactly which parties observe the holder and context and what happens under issuer/gateway collusion. Knowledge of signature and holder alone should be insufficient for a thief lacking `s`, conditional on preimage/binding and soundness assumptions; willing holder sharing remains possible.

## 6. Time, anti-replay and state assumptions

`Challenge.Validate()` checks syntax and a positive expiry, not current time, server issuance, single use or nonce randomness. `PublicStatement` merely reconstructs public values. A full acceptance implementation must check that the challenge is in server-held state for that task and is not expired under the trusted clock; verify the proof before committing, then atomically record task-scoped nullifier and consume challenge together with acceptance. If gateway state is a single-process map, state that scope and test concurrent interleavings; durable multi-instance semantics are not established by a mutex in one process. On proof failure do not consume a legitimate challenge. A repeated challenge must be rejected even if a different valid credential yields a fresh nullifier. Use CSPRNG nonce generation rather than just syntax validation.

**Required tests:** unknown/expired nonce; reused nonce with a different credential; same task and same credential under two independently fresh nonces; two concurrent submissions with different nonces but identical task nullifier; failed proof followed by valid retry; two tasks with same user; invalid proof and stale challenge leave state unchanged. Test both semantic state and return values. If multiple gateway processes or persistence are not implemented, do not claim distributed exactly-once behavior.

## 7. Bounds and implementation notes

Current `ToBinary(...,32)` constraints on each event and policy endpoint restrict unsigned values to `0..2^32-1`. For any two such values their absolute difference is at most `2^32-1`, meeting the advertised `NewBoundedComparator` bound; comparisons appear internally consistent provided `ToBinary` constraints are retained. Test equality at both endpoints, min/max, reversed policy bounds, values `2^32`, and native/field-encoded negative values. Interpret spatial coordinates through a defined projection, units, quantization and reference frame. Integer time must have a stated epoch/unit and be within 32-bit range. This is a 3D rectangular policy, not an irregular road polygon, arbitrary region, continuous GPS accuracy or an uncertainty box proof.

`digestToField` reduces SHA-256 output modulo BN254 scalar field; document this as the protocol encoding, not an injective mapping or a full 256-bit collision guarantee. Go JSON encoding must be fixed as a versioned canonical wire format; normalize hex nonces or use decoded fixed-length bytes to avoid cross-implementation ambiguities. Domain tags protect different field-hash purposes only if serialization is fixed, field counts/positions are explicit, and message/signature hashing matches the tested native signer.

The issuer signs a location/time claim; absent a trusted observation protocol, it could sign caller-supplied false data. Altering bound report or stealing a receipt without `s` is a suitable cryptographic negative test; copying a legitimate receipt along with voluntary disclosure of `s`, real-time relay, copied/stale sensor data, malicious certified issuer, issuer key theft and bad physical calibration are not generically blocked. Do not report these as tested protections.

## 8. Minimal acceptance and reporting gate

1. Real Groth16 compile/solve/prove/verify for a positive witness and genuine adversarial negatives, with fixed tool/library versions and raw outputs.
2. Authority pinning, valid issuer registration and predicted neutral/small-order key tests.
3. Actual verifier statement reconstruction tests and durable/atomic anti-replay tests for the implemented scope.
4. No invented provenance, anonymous-credential, anti-Sybil, end-to-end vehicle, encrypted report, 128-bit or post-quantum claims. The code enforces a signed event relation conditioned on issuer and enrollment trust; event truth remains external.
5. Security discussion should say this report binds the signed event to the supplied report and context; it does not certify sensing occurred or the report is factually correct.
