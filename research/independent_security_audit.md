# Independent security audit of the event-report prototype

Snapshot inspected on 2026-11-04: `paper_a/event_report/prototype/circuit.go`, `native.go`, `gateway.go` and `circuit_test.go`, together with the locally cached gnark v0.14.0 and gnark-crypto v0.19.0 source. The implementation was under active development, so findings must be checked against the final revision. This is a targeted source review, not a proof of security or an exploit demonstration. The earlier `circuit_security_review.md` contains complementary details and suggested test cases.

## Main findings

1. **An authenticated receipt is only as meaningful as the issuer's observation.** The actual `Fixture.Assignment` constructs the authorization certificate and all three signatures locally, with access to both signing keys, on a caller-specified event and arbitrary report bytes. This is useful for testing the algebra, but it is not a deployment of an independently observing RSU, credential authority or trusted sensor. In particular, a receipt containing a fresh challenge shows that a signing operation used the challenge; it does not establish that the sensing data were measured then. Use the terms synthetic or software-generated in experimental descriptions. Do not infer physical presence, truthful measurements or resistance to real-time relay from accepting a proof.

2. **The verification boundary is essential.** The circuit accepts task identifier, bounds and context as independent public inputs. It checks a signature on context and event and computes the task-scoped nullifier, but does not itself derive the context from the supplied task policy, challenge and exact received bytes. `Gateway.Submit` reconstructs them from its trusted task, stored challenge and received bytes before verification, which is the intended defense. No code path may instead trust a prover-selected public witness. Test mutations of each task bound, task identifier, nonce, expiry, authority key, payload and nullifier with *newly reconstructed* verifier inputs. Specify SHA-256-to-field reduction and the versioned JSON serialization in the protocol; the latter is a Go-specific deterministic encoding here, not a demonstrated cross-language canonicalization standard.

3. **Key and signature input validation deserves explicit constraints.** At this snapshot, the code checks the private issuer point on the curve, rejects identity and attempts an order multiplication; this last check used `curve.ScalarMul(point, curve.Params().Order)` and triggered a solver panic on the positive test according to the running investigation. A direct fixed-constant double-and-add sequence can avoid the scalar-multiplication hint reduction but must itself be tested for valid generated keys, identity, nonidentity low-order points and mixed-torsion points. `eddsa.Verify` in the pinned gnark library checks an intermediate point, and uses a cofactor-cleared equation, but does not explicitly call `AssertIsOnCurve` on the input signature `R` or the public key. Independently enforce that both are on curve; for authorized keys check prime-subgroup membership and nonidentity. This is hardening based on source inspection, not a demonstrated arbitrary-key signature forgery. The authority key must be pinned from trusted configuration.

4. **Native public-key parsing is not sufficient validation.** `NewGateway` checks only authority byte length, whereas its comment implies parsing validation. `PublicStatement` uses gnark `PublicKey.Assign`; its underlying BN254 `PointAffine.SetBytes` returns an error for short input but does not itself check `IsOnCurve`, nonidentity, prime subgroup or canonical input. Explicitly decode, reject noncanonical encodings by re-encoding and comparison, check on-curve/nonidentity, and verify `[order]P` is identity with the native library before accepting a configured authority; handle any decoding failure as an error. A pinned malformed trusted authority may invalidate the authorization model even if it is not a remotely selectable user input.

5. **Digest binding is not payload confidentiality.** `ContextField` includes an unsalted SHA-256 of report bytes. Given all other transcript fields, a verifier who suspects a small set of possible reports can test guesses against the public context. If plaintext report bytes are submitted, no payload confidentiality has been achieved. An actual authenticated-encryption envelope can address this for recipients without the secret key, assuming secure key establishment, random unique nonces and authenticated context. The proof must bind the actual envelope bytes accepted, and an authorized recipient must authenticate/decrypt it; a valid proof by itself does not establish valid AEAD ciphertext. Report visible length and metadata, recipient access and key-setup scope accurately.

6. **Replay state is instance-local and volatile.** The new gateway holds a mutex across proof verification and the challenge/nullifier update, which gives a plausible single-instance atomic transition when the process stays alive. It does not establish durable or multi-process exactly-once semantics. Require actual tests for duplicate nullifiers across two challenges, a consumed nonce with two credentials, concurrent submissions, unknown/expired challenges, failed verification followed by retry, and independent tasks. Neither a mutex nor a single successful proof is evidence of resilience to process crash or a distributed deployment. Holding the lock through cryptographic verification serializes all requests, so do not claim scalable throughput without actual measurement.

7. **The eligibility predicate is discrete and rectangular.** Three unsigned 32-bit values are compared inclusively against public bounds. A meaningful real-world location/time claim requires a defined coordinate system, discretization, epoch, units and trusted issuer measurement; there is no polygon membership or physical proximity verification in the inspected circuit. The user-supplied TST-Audit paper already contains an abstract anonymous, task-relevant micro-proof and scoped nullifiers; avoid novelty claims for those primitives or for coverage auditing.

8. **Anonymity depends on roles and assumptions.** A private issuer public key inside the witness hides that field from the verifier only through the proof's zero-knowledge property. Public task policy, ciphertext length, communication metadata and other public inputs can still be identifying. The nullifier intentionally links repeated attempts in the same task; cross-task unlinkability needs an explicit assumption on the keyed-by-secret MiMC construction and high-entropy secret generation, and cannot be established by observing that two sample outputs differ. `Secret != 0` in the circuit does not prove entropy. One credential per person, enrollment honesty, key compromise, credential sharing and revocation are external assumptions or unimplemented controls.

## Verification targets before quantitative claims

- Recompile the final circuit and run an actual Groth16 proof and verifier check after any code changes; record backend, constraint count, setup and trial metadata.
- Exercise actual admissible and invalid witnesses, including identity and low-order certified issuers and malformed public authority encodings, as well as boundary, overflow and authenticated out-of-policy cases. A witness-solver failure and a real proof verification test measure different things and should be labeled accordingly.
- Separately check AEAD modification/incorrect key and actual gateway state transitions, and report only modules actually timed and transmitted. Do not treat issuer/authority signing inside the fixture as measured road-side issuance.
- Every security statement should condition on trusted configuration, signature unforgeability, the implemented circuit and gateway binding, and the applicable hash/SNARK assumptions. A formal reduction is still required to present a theorem as proven.
