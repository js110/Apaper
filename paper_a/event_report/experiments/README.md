# Event-report proof experiment

This is a reproducible software benchmark of the actual BN254/Groth16 circuit in `../prototype`, not a vehicular field test or a measurement of a roadside unit. The random authority and issuer keys and all signed event coordinates are generated in software. The experiment does not establish the physical truth of the event, report confidentiality, production readiness or throughput under a network workload.

From `../prototype`, run:

```sh
EVENT_BENCH_RUNS=30 go test -run '^TestBenchmarkExperiment$' -count=1 -timeout=30m -v | tee ../experiments/benchmark.log
```

Set `GOMAXPROCS` if comparing runs with a fixed worker limit. The first uncached run requires the Go modules pinned by `go.mod` and `go.sum`; package downloads and Go compilation are excluded from reported timings. Set `GOMODCACHE` or `GOPROXY` as appropriate for the network. To ensure a shell pipeline returns a failing Go test exit status, enable `pipefail` or redirect both streams to the log instead of piping through `tee`.

The opt-in test compiles the R1CS and performs circuit-specific Groth16 setup once; their wall-clock durations are reported separately and are not repeated 30 times. It creates one software fixture, runs one warm-up, then produces and verifies 30 proofs over different synthetic report/context statements. Each timed proof and verification is checked for an error and every proof is serialized using the gnark `WriteTo` method. Each raw sample logs proving and verification elapsed nanoseconds, serialized proof bytes and separately serialized public-witness bytes. Statements, signatures, witness creation and serialization are outside the prove and verify intervals; task creation, issuance, networking, state-store checks, encryption, key distribution and real hardware sensing are not measured. The source SHA-256 values in the log identify the relevant circuit, fixture, module files and experiment harness. Any subsequent circuit change requires rerunning the experiment.

The Groth16 setup generated here is local to a research run and does not demonstrate a secure production setup ceremony. Repeat on the desired platform and under a controlled load; sample timings may vary with scheduling, thermal conditions and background processes. Compare methods only after matching their functionality, threat assumptions, operations measured and runtime environment.

## Additional controlled experiments

- `context_ablation.log`: the full relation and a purpose-built no-context circuit were checked under original, substituted report, substituted challenge and substituted task contexts. The attacker retains a valid credential and original receipt, not the issuer key. The full relation is checked with the R1CS solver; the ablated relation is additionally proved and verified using Groth16. Run `go test -run '^TestContextBindingAblation$' -count=1 -v` in `prototype/`.
- `ablation_cost.log`: the full rectangle circuit and `bearerCircuit` use the same fixture, task and event and a fixed valid witness. Each uses a separately generated local setup, one warm-up and 30 sequential measured proofs and verifications. Run `EVENT_BINDING_COST=1 go test -run '^TestBindingCostExperiment$' -count=1 -v` in `prototype/`. Timed operations exclude fixture construction, setup and witness creation. This is an internal ablation, not an implementation of a published baseline.
- `region_scale_{4,6,8}.log`: 30 proof and verification measurements per independently compiled region circuit, with one warm-up and one setup each. The inputs are synthetic; all cells are populated, and the same event is proved. Run `python3 experiments/run_region_scaling.py` from the project directory. The script changes the compile-time depth in temporary copies; the eight-level production prototype is unchanged. Source hashes in each log identify the generated variant.
- `context_hiding_extensions.log`: hidden-context variants of all four circuits (rectangle, region, accountability, active set). The issuer signs (constant, holder, event); the extension relations and the public-input layout are unchanged, so the existing gateways verify the hidden proofs with a hidden verification key. Region, accountability and active each run 30 acceptance-path measurements with a fresh challenge, report and re-signed receipt per run, plus substituted-context, substituted-holder and duplicate-nullifier checks; the rectangle variant uses the fixed-witness prove/verify methodology of `benchmark.log`. Run `EVENT_HIDDEN_EXT_RUNS=30 go test -run '^TestHiddenExtensionsExperiment$' -count=1 -timeout=60m -v` in `prototype/`. These are research candidates; the benchmark does not measure the privacy gain.
- `protocol_comparison.log`: same-task, same-process three-arm comparison of the shared-context active circuit, the hidden-context active circuit, and a trusted-issuer plus task-pseudonym baseline without zero-knowledge proofs; 30 measured runs per arm after one warm-up. Also records baseline rejection checks (tampered report, forged signature, cross-task receipt, duplicate pseudonym, revoked identity), the pre-revocation receipt behaviour, and an issuer cross-task linkability check. Run `EVENT_COMPARISON_RUNS=30 go test -run '^TestProtocolComparisonExperiment$' -count=1 -timeout=60m -v` in `prototype/`. The baseline is an internal control, not an implementation of a published scheme.
- `interleaved_comparison.log`: two-arm randomized-order control of the shared-context and hidden-context active circuits. Each round flips a random bit to decide which arm runs first; 100 paired rounds, fresh challenge/report/re-signed receipt per run, same task and event shape as `protocol_comparison.log`. Run `EVENT_INTERLEAVED_RUNS=100 go test -run '^TestInterleavedArmComparison$' -count=1 -timeout=60m -v` in `prototype/`. Statistics (paired t, Wilcoxon signed-rank, 95% CI, per-arm order-effect Welch tests) are recomputed by `python3 experiments/analyze_interleaved.py` from the log; the recorded output is `interleaved_stats.txt`. Both tests live in `prototype/load_realism_test.go` and are opt-in.
- `gateway_load_memory.log`: load and memory profile of the hidden-context active circuit (68,262 constraints) in a separate session. Records (a) 100 in-process `SubmitAndOpen` accepts with mean latency and throughput under the single gateway mutex, (b) stateless verification throughput sharded over 1/2/4/8 worker goroutines with 2,000 verifications per level, and (c) prove-time resident-memory deltas for cold and warm runs plus cumulative allocation and process peak RSS. Run `EVENT_LOAD_SUBMITS=100 EVENT_LOAD_VERIFY_RUNS=2000 EVENT_LOAD_PROCS=1,2,4,8 go test -run '^TestGatewayLoadAndMemory$' -count=1 -timeout=60m -v` in `prototype/`. All measurements are single-machine, in-process; network transport and connection management are not included.
- `nonsnark_baseline.log`: four-arm comparison that adds two anonymous non-SNARK baselines to the hidden-context arm and the weak trusted-issuer control, answering the reviewer request for a stronger baseline. `bbs_credential` implements a BBS+ selective-disclosure credential over BLS12-381 (`trustbloc/bbs-signature-go`, `bbs12381g2pub`): an 8-attribute vector with 7 disclosed, issued against a challenge digest, report digest and event triple, verified at the gateway. `privacy_pass` implements RFC 9578 section 5 token type `0x0001` (VOPRF P-384/SHA-384, `cloudflare/circl/oprf`) with a separate issuer redemption step, since §5.4 verification needs the issuer private key. 30 measured runs per arm after one warm-up, same task and event shape and the same three-message handshake as `protocol_comparison.log`, plus one extra issuer RPC for the Privacy Pass arm (4 round trips). Also records per-arm rejection and linkability probes (BBS+: tampered report, forged nickname, second credential per task, cross-task credential, revocation, issuer-side nickname derivation; Privacy Pass: issuer blindness of the TokenRequest, Origin acceptance without the issuer key, replay with and without the issuer callback, tokens redeemable per challenge) and a determinism probe that documents that this BBS+ build's `VerifyProof` is not idempotent across calls on a shared scheme instance. Run `EVENT_NONSNARK_RUNS=30 go test -run '^TestNonSnarkAnonymousBaseline$' -count=1 -timeout=20m -v` in `prototype/`. Statistics are recomputed by `python3 experiments/analyze_nonsnark.py experiments/nonsnark_baseline.log experiments/nonsnark_baseline_stats.txt`; the recorded output is `nonsnark_baseline_stats.txt`. The two arms are implementations of published constructions, but each is a research harness in this repository, not a deployed issuer, Origin or verifier; the BBS+ and Privacy Pass curves differ from the BN254 zero-knowledge arm, so latencies compare mechanisms rather than curves.

The experiments were run sequentially on the Apple M1 system recorded in the region logs; they are not field or network measurements. `tests_after_ablations.log` records the non-opt-in test suite after adding the new tests.

## Role-view and candidate security checks

- `context_linkability.log`: `go test -run '^TestIssuerGatewayContextLinkage$' -count=1 -v` demonstrates a two-record synthetic join when issuer and gateway share the current protocol's context records.
- `context_hiding_candidate.log`: `go test -run '^TestHiddenContextCandidate$' -count=1 -v` checks an independently implemented base-circuit research candidate. It is not the current manuscript's main protocol, and is not an experimental proof of collusion resistance. See `../安全修订与候选方案.md` for conditions and outstanding work.
